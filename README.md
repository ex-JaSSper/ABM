# ABM-сервис — управление работой с целевыми аккаунтами

Лёгкий ABM-инструмент для небольшой команды (1–5 человек): стратегия, гипотезы, компании, ЛПР, CRM-воронка и командная доска задач в одном интерфейсе.

Работают две независимые плоскости:

1. **Плоскость компании** — воронка продаж: сигнал → отвес → в работу → разбор → цикл задач-касаний → договорённость → выручка.
2. **Плоскость гипотез** — измеритель стратегии: гипотеза → задача → подзадачи → прогресс. Живёт отдельно от воронки; факт «трекинг-задач» набирается автоматически из выполненных касаний.

---

## Живой стек

- **Приложение:** один самодостаточный файл [`web/index.html`](web/index.html) — ванильный JS, без сборки. Графики (воронка, прогресс-бары) нарисованы на CSS. XLSX-импорт — SheetJS, клиент БД — supabase-js (оба с CDN).
- **База данных:** **Supabase** (Postgres + REST + RLS). Схема — [`supabase/db-setup.sql`](supabase/db-setup.sql).
- **Хостинг:** **Render** Static Site (публикует папку `web/`).
- **Дизайн:** светлый воздушный минимализм (Inter, пастельный индиго-акцент, тонкие линии) — акцент на ясности и фокусе.

Данные общие для всей команды и сохраняются между устройствами (пишутся напрямую в Supabase; фоновая синхронизация с индикатором «Сохранение… / Сохранено»).

## Возможности

| Раздел | Что делает |
|---|---|
| **Обзор** | KPI план/факт, метрики, две воронки, отложенные ЛПР, фокус и прогресс гипотез |
| **Стратегия** | Название, описание, ожидаемый эффект; переключение между стратегиями; загрузка стратегии из JSON; шаблоны импорта |
| **Гипотезы** | Гипотеза → задачи → подзадачи; статусы и приоритет A/B/C; факт `tracked`-задач считается автоматически из привязанных касаний/встреч; создание задач и подзадач |
| **Сигналы** | Очередь новых компаний; отвес «В работу / Не подходит»; сетка 2/3 колонки; клик по карточке → детали; «Удалить все сигналы» |
| **Компании** | Таблица + страница компании (вкладки: Досье / ЛПР / Действия). Несколько ЛПР на компанию, счётчики касаний/встреч по каждому |
| **Контакты** | Все ЛПР, фильтр по компании, статус, unmatched |
| **CRM** | Канбан ЛПР: перенос в этап фиксирует состоявшееся действие; «Отложенные» хранят контакты, по которым решение пока не принято |
| **Задачи** | Отдельный канбан командных задач по стратегии и гипотезам |

**Импорт:** Excel/CSV с компаниями и контактами (одной таблицей или двумя листами) — идемпотентно по № компании. Стратегии — из JSON (гипотезы + задачи + подзадачи).

---

## Ключевая доменная логика

- **CRM как источник истины:** перенос карточки ЛПР в этап фиксирует завершённое касание, встречу, договорённость или сделку. Будущие шаги в модальном окне не создаются.
- **Отложенные:** отдельная колонка для ЛПР, по которым пока не определено дальнейшее действие. После выбора действия карточка переносится из неё прямо в нужный этап.
- **Метрики (с повторами):** `+1` в момент завершения задачи по её типу (новые/повторные касания и встречи, договорённости, выручка).
- **Воронки (уникальные, накопительно):**
  - *компании* — компания входит в стадию, если хотя бы с одним её ЛПР совершено такое действие;
  - *контакты* — каждый ЛПР считается по максимально достигнутому действию.
- **Автотрекинг гипотез:** задача по компании ссылается на гипотезу и её задачу → факт `tracked`-задачи гипотезы набирается сам из выполненных касаний/встреч/договорённостей.

## Модель данных (Supabase)

```
strategy ─┬─ kpi_target
          └─ hypothesis ─ hyp_task ─ hyp_subtask
company ─ contact
company_task → (company, contact, hypothesis, hyp_task)
board_task → (strategy, hypothesis, hyp_task)
```

Полная схема с ограничениями, индексами и RLS — в [`supabase/db-setup.sql`](supabase/db-setup.sql). Рабочее пространство общее (мультиарендность в MVP не нужна).

## Быстрый старт

### 1. База (Supabase)
1. supabase.com → New project.
2. SQL Editor → выполнить [`supabase/db-setup.sql`](supabase/db-setup.sql) (создаёт таблицы, RLS и стартовую стратегию).
3. Project Settings → API → взять **Project URL** и **Publishable (anon)** ключ.

### 2. Подключение приложения
URL и публичный ключ прописаны в начале `<script>` в [`web/index.html`](web/index.html):
```js
const SB_URL = 'https://<ваш-проект>.supabase.co';
const SB_KEY = 'sb_publishable_...';
```
Публичный ключ безопасно хранить в клиенте — доступ ограничен политиками RLS.

### 3. Локально
SQLite используется только для локальной разработки. Его схема зеркалирует Supabase; инструкция находится в [`local/README.md`](local/README.md). Файл базы и демонстрационные данные в Git не попадают.

### 4. Деплой на Render
New → **Static Site** → подключить репозиторий → **Publish Directory: `web`** → Create. Хеш-роутинг (`#/…`) не требует серверных rewrite-правил. Конфиг-шаблон — [`render.yaml`](render.yaml).

## Форматы импорта

- **Excel/CSV (компании + контакты):** колонки распознаются по названиям. Шаблон скачивается из раздела «Стратегия» (кнопка «Шаблон Excel»).
- **Стратегия (JSON):** гипотезы → задачи → подзадачи. Спецификация и пример — [`supabase/strategy-example.json`](supabase/strategy-example.json). Кратко:
  - задача с `"tracked": "touch"|"meeting"|"agreement"` → факт считается автоматически;
  - задача с `"subtasks": [...]` → ручная, факт = число отмеченных подзадач;
  - `priority`: `A`/`B`/`C`; `status` гипотезы: `idea|in_work|validated|paused|rejected`.

## Безопасность и следующие шаги

- Сейчас — режим **без логина** (доступ по публичному ключу через RLS-политики `anon`). Для боевого запуска: включить Supabase Auth (email), создать пользователей и заменить `anon`-политики на `authenticated` (заготовка — в `supabase/schema.sql`).
- Бэклог: проверка благонадёжности компании (внешний сервис), realtime-обновления между пользователями, экран входа.
