# ТЗ: ABM-сервис — «движок следующего действия»

Спека для реализации в Claude Code. Референс-схема процесса: `abm-process-v3.drawio`.

---

## 1. Суть продукта

Лёгкий ABM-сервис для **малого числа пользователей** (1–5), который просто заливается на хостинг. Это **не CRM-хранилище**, а движок, который держит фокус оператора: гарантирует, что ни одна компания «в работе» не висит без следующего шага, и ранжирует, с кем работать прямо сейчас.

Одна мысль, которой проверяется любое решение: *помогает не потерять фокус или размывает его?*

Работают две независимые плоскости:

1. **Плоскость компании** — воронка продаж: сигнал → отвес → в работу → разбор → цикл задач-касаний → договорённость → выручка. Двигает статусы и метрики.
2. **Плоскость гипотез** — измеритель стратегии: гипотеза → задача → подзадачи с ручными галочками → прогресс-бар. Живёт отдельно, не связана стрелками с воронкой.

---

## 2. Технологический стек (рекомендация, можно заменить)

- **Frontend:** React + Vite + TypeScript + Tailwind. Графики — Recharts. Парсинг xlsx — SheetJS (`xlsx`).
- **Backend/БД:** Supabase (Postgres + Auth + Storage). Причина: у заказчика есть опыт, управляемый хостинг, REST/Realtime «из коробки».
- **Деплой:** фронт на Vercel/Netlify, БД — Supabase managed.
- **Проще/полностью self-hosted альтернатива:** SQLite + один сервер (Node/Express или FastAPI), единый Docker-образ на VPS. Выбрать, если не хочется внешних сервисов.
- **Auth:** минимальный. Few users — достаточно одного аккаунта или простого списка пользователей. Мультиарендность не нужна.

Доменная логика и модель данных ниже — от стека не зависят.

---

## 3. Навигация (боковое меню)

Всё через левое боковое меню. Разделы:

1. **Обзор / Дашборд** (главная) — метрики план/факт, воронка, экран «Фокус».
2. **Стратегия и гипотезы** — гипотезы с прогресс-барами, их задачи/подзадачи.
3. **Сигналы** — очередь новых компаний на первичный отвес.
4. **Компании** — таблица компаний = страницы компаний.
5. **Контакты** — таблица контактов (ЛПР), фильтр по компании.
6. **Задачи** — все задачи по компаниям (трекер), в т.ч. открытые следующие шаги.

---

## 4. Модель данных

Postgres-нотация. FK и enum обязательны.

### 4.1. Стратегия и KPI

```
strategy(
  id, name, quarter,            -- напр. '2026-Q3'
  created_at
)

kpi_target(
  id, strategy_id -> strategy,
  kpi_key,                       -- enum: new_touches | new_meetings | repeat_meetings | agreements | revenue
  unit,                          -- 'шт.' | 'руб.'
  plan_value numeric,
  prev_q_value numeric           -- «прошлый Q» для дашборда
)
```

### 4.2. Плоскость гипотез (независимая)

```
hypothesis(
  id, strategy_id -> strategy,
  title, description,
  is_active bool,
  created_at
)                                 -- прогресс НЕ хранится, вычисляется из задач

hyp_task(
  id, hypothesis_id -> hypothesis,
  title, description, sort_order
)

hyp_subtask(
  id, hyp_task_id -> hyp_task,
  title,
  is_done bool default false,     -- ручная галочка
  sort_order
)
```

Прогресс:
- `progress(hyp_task)` = кол-во `is_done` подзадач / всего подзадач.
- `progress(hypothesis)` = среднее по прогрессу её задач (или сумма done-подзадач / сумма всех — выбрать одно, задокументировать).
- Галочки ставит пользователь **вручную**. Никакой авто-связи с задачами по компании в MVP.

### 4.3. Компании и контакты

Поля колонок берём 1:1 из загружаемых таблиц (см. раздел 5).

```
company(
  id,
  ext_no,                         -- № из таблицы
  name,                           -- 'компания'
  priority,                       -- 'приоритет' (A/B/C)
  segment, category, geography,
  why_fit,                        -- 'почему подходит'
  signal_note,                    -- 'сигнал / наблюдение'
  relevant_hypothesis_text,       -- 'релевантная гипотеза' (просто текст из файла)
  what_to_check,                  -- 'что проверить / предложить'
  who_to_find,                    -- 'кого искать для входа'
  extended_reason,                -- 'расширенный повод для сообщения'
  first_message_template,         -- 'заготовка первого сообщения'
  second_message_template,        -- 'заготовка второго сообщения'
  funnel_stage,                   -- enum, см. 4.5
  is_excluded bool default false,
  excluded_reason,
  created_at, last_activity_at
)

contact(
  id,
  company_id -> company,          -- матч по (ext_company_no|company_name), см. 5.3
  ext_company_no,                 -- '№ компании'
  company_name,                   -- 'Компания'
  priority, segment,
  role_target,                    -- 'Роль из столбца K / цель'
  contact_no,                     -- 'Контакт №'
  full_name, position,
  phone, email, telegram, tenchat, network, linkedin, other_social,
  source,                         -- 'Источник контакта'
  last_digital_trace, last_trace_date, check_date,
  confidence,                     -- 'Уверенность'
  comment,                        -- 'Комментарий / почему подходит'
  how_to_get                      -- 'Если данных нет — как добрать'
)
```

У компании **несколько контактов** (одна-ко-многим). На странице компании — список её ЛПР; фильтр по компании выгружает всех её контактов.

### 4.4. Задачи по компании (двигают воронку)

```
company_task(
  id,
  company_id -> company,
  title, description,             -- задачу описываем сами
  type,                           -- enum, см. ниже
  status,                         -- enum: planned | waiting | done | cancelled
  result_note,                    -- «хорошо пообщались» и т.п.
  is_next_step bool,              -- открытый «следующий шаг»
  due_at nullable,
  created_at, completed_at
)
```

`company_task.type` (выбирается **при планировании**):

| type | двигает метрику | двигает стадию воронки |
|---|---|---|
| `analyze_signal` (разобрать сигнал) | — | → in_work |
| `touch_new` (новое касание / первое сообщение) | `new_touches +1` | → touched |
| `touch_repeat` (повторное касание) | `repeat_touches +1` | — |
| `meeting_new` (новая встреча) | `new_meetings +1` | → met |
| `meeting_repeat` (повторная встреча) | `repeat_meetings +1` | — |
| `agreement` (договорённость / пилот) | `agreements +1` | → agreement |
| `custom` (свободная) | — | — |

**Ключевое правило:** метрика инкрементится в момент `status = done` (завершения задачи), по её `type`. Не при планировании, не «на глаз».

Выручка фиксируется отдельно (поле/событие оплаты) → стадия `revenue`.

### 4.5. Стадии воронки

`company.funnel_stage` — enum, текущая максимально достигнутая стадия:

```
new_signal   -- загружена, не разобрана
rejected     -- отсеяна на отвесе (терминал)
in_work      -- взята в работу / в разборе (статус «Отобрано»)
touched      -- есть >=1 завершённое касание
met          -- есть >=1 завершённая встреча
agreement    -- договорённость / пилот
revenue      -- оплата → платёжеспособный клиент
excluded     -- выбыла в процессе (терминал)
```

Стадия только растёт (кроме перехода в терминальные `rejected`/`excluded`). Повторные касания/встречи стадию не меняют.

## 5. Импорт данных

Три типа загрузки. Все — Google-таблица (ссылка на опубликованный CSV или Sheets API) **или** файл `.xls` / `.xlsx`.

### 5.1. Стратегия + гипотезы
Опционально; задачи/подзадачи гипотез можно и не грузить, а завести вручную. Без стратегии сервис работает в режиме просмотра/загрузки, но гипотезы, прогресс и KPI без неё бессмысленны.

### 5.2. Компании
Лист вида «ABM база». Колонки (порядок как в файле):
`№, приоритет, сегмент, категория, компания, география, почему подходит, сигнал / наблюдение, релевантная гипотеза, что проверить / предложить, кого искать для входа, расширенный повод для сообщения, заготовка первого сообщения, заготовка второго сообщения`.
После загрузки создаётся таблица «Компании», **каждая компания = новый сигнал** (`funnel_stage = new_signal`).

### 5.3. Контакты
Лист вида «Контакты — пищепром». Колонки:
`№ компании, Компания, Приоритет, Сегмент, Роль из столбца K / цель, Контакт №, Имя и фамилия, Должность, Телефон, Почта, Telegram, TenChat, Сетка, LinkedIn, Другие соцсети, Источник контакта, Последний цифровой след, Дата последнего следа, Дата проверки, Уверенность, Комментарий, Если данных нет — как добрать`.

**Матч контакт → компания:** по `№ компании` (в приоритете) и/или нормализованному `Компания`. В данных связь всегда есть, сценарий «сироты» не реализуем в MVP. Если совпадения не нашлось — контакт помечается `unmatched` и показывается в отдельном списке (простая заглушка, без сложной логики).

Импорт должен быть идемпотентным по `ext_no` / `(ext_company_no, contact_no)` — повторная загрузка обновляет, а не плодит дубли.

## 6. Бизнес-логика — процесс по компании

Соответствует секции ① схемы `abm-process-v3.drawio`.

1. **Сигналы.** Все загруженные компании попадают в раздел «Сигналы» как `new_signal`.
2. **Первичный отвес.** Оператор смотрит сигнал и решает вручную:
   - *не подходит* → `rejected` (терминал, уходит из воронки);
   - *подходит* → жмёт **«В работу»**.
   *(Проверка благонадёжности через Chekko — бэклог, см. раздел 10.)*
3. **«В работу»** автоматически создаёт первую задачу `analyze_signal` («Разобрать сигнал»), компания → `in_work` (статус «Отобрано»).
4. **Разбор сигнала.** Оператор вчитывается в компанию, определяет предложение (с чем идём). Результат фиксируется в `result_note`, задача завершается.
5. **Механика «Следующий шаг».** При завершении **любой** задачи всплывает модалка:
   - *назначить следующий шаг* → создаётся новая `company_task` с выбранным `type` (касание / повт. касание / встреча / повт. встреча / договорённость / custom), `is_next_step = true`;
   - *или* **исключить компанию** → `excluded` + причина (доступно на любом шаге).
6. **Выполнение шага.** Задача переходит в `waiting` (ждёт ответа). При завершении (`done`) — инкремент метрики по `type` и, если применимо, рост `funnel_stage` + `last_activity_at = now`.
7. **Цикл** повторяется (касания/встречи «крутятся»), пока не `agreement` → фиксация оплаты → `revenue` (**клиент платёжеспособен**), либо `excluded`.

**Инвариант фокуса:** у любой активной компании (`in_work..agreement`, не excluded/rejected/revenue) всегда должна быть ровно одна открытая задача (`planned`/`waiting`). Ноль открытых = компания «зависла».

## 7. Бизнес-логика — плоскость гипотез

Соответствует секции ② схемы. Полностью отдельно от воронки.

- Гипотеза формулируется измеримо («продукт X понравится сегменту Y»).
- Внутри — задачи («предложить X»), внутри задач — подзадачи-чеклист («провести 10 касаний»).
- Пользователь ставит галочки вручную → двигается прогресс задачи → прогресс-бар гипотезы.
- Гипотезы можно добавлять / удалять / редактировать в рамках стратегии.
- Прогресс гипотезы выводится на дашборд рядом со стратегией.

*В MVP касания в подзадачах гипотезы считаются вручную и не связаны с авто-метриками из раздела 6. Связь «одна задача ↔ несколько гипотез» — бэклог.*

---

## 8. Метрики и воронка (две разные агрегации)

Соответствует секции ③ схемы. Обе выводятся на главной.

### 8.1. Метрики (счётчики, с повторами)
`+1` при завершении задачи по её `type`:
- Новые касания (первое сообщение) — `count(type=touch_new, status=done)`
- Повторные касания — `count(type=touch_repeat, done)`
- Новые встречи (проявленный интерес) — `count(type=meeting_new, done)`
- Повторные встречи — `count(type=meeting_repeat, done)`
- Выход на договорённости (договор/пилот) — `count(type=agreement, done)`
- Выручка — `sum(revenue)`

### 8.2. Воронка (уникальные клиенты, без повторов)
Считаем компании, достигшие стадии хотя бы раз:
`Выгружено` (все) → `Перенесено в разбор` (`stage >= in_work`) → `Касание` (`stage >= touched`, уник.) → `Встреча` (`stage >= met`, уник.) → `Выручка` (`stage = revenue`, уник.).

Правило: клиент входит в стадию воронки **при первом** достижении; повторные действия туда не идут (они только в метриках 8.1).

> Решение к уточнению: воронка показывает **максимально достигнутую** стадию (накопительная конверсия). Если нужен срез «где клиент застрял сейчас» — это отдельный подсчёт по текущему `funnel_stage`; в MVP делаем накопительный.

## 9. Механика фокуса

- **Зависшая компания** = активная (`in_work..agreement`, не терминальная) и без открытой задачи, **или** с просроченной (`due_at < now`).
- **Приоритет фокуса** = `вес_стадии × давность_простоя(дней)`. Чем глубже в воронке и дольше без движения — тем выше и «настырнее».
  Пример весов: in_work=1, touched=2, met=3, agreement=5.
- **Экран «Фокус»** (на главной) — список активных компаний, отсортированный по приоритету, зависшие сверху; из карточки сразу «назначить шаг» или «исключить».
- Модалка «назначь следующий шаг» при закрытии задачи — способ не дать инварианту сломаться. Пропустил → компания всплывает в «Фокусе» как зависшая.

## 10. Экраны (что на них)

- **Обзор / Дашборд:** таблица KPI план/факт (раздел 11), блок воронки (8.2), блок метрик (8.1), экран «Фокус» (9), прогресс гипотез.
- **Сигналы:** очередь `new_signal`; действия «В работу» / «Не подходит».
- **Компании:** таблица + страница компании (все поля, список контактов, история задач, текущий статус, кнопка «следующий шаг»/«исключить»).
- **Контакты:** таблица всех контактов, фильтр по компании, приоритету, сегменту.
- **Стратегия и гипотезы:** гипотезы с прогресс-барами, дерево задача→подзадачи с чекбоксами.
- **Задачи:** трекер всех `company_task`; фильтры по статусу/типу/компании; видны открытые следующие шаги и просрочки.

## 11. Дашборд KPI план/факт

Повторяет прикреплённый макет. Таблица со столбцами:
`KPI | Ед. | План Q | Факт Q | Выполнение % | ΔQ | Прошлый Q`.

Строки: Количество новых касаний, Количество новых встреч, Количество повторных встреч, Выход на договорённости, Выручка.
- `План Q`, `Прошлый Q` — из `kpi_target`.
- `Факт Q` — из метрик (8.1).
- `Выполнение %` = факт/план. `ΔQ` = факт − прошлый Q.
Плюс верхние плашки: «Обработано сигналов N / ещё M ждут решения», «Касаний записано в сервисе», кнопки «Разобрать сигналы» / «Открыть задачи».

---

## 12. Бэклог (в MVP не делаем, но не ломать под них модель)

- Проверка благонадёжности компании через внешний сервис (Chekko) на этапе отвеса.
- Тёплый / холодный трек (разные циклы входа).
- Связь «одна задача ↔ несколько гипотез» (авто-подтягивание касаний из воронки в прогресс гипотез).
- Система баллов/скоринга сигналов — **исключена сознательно**, не возвращать.

---

## 13. Критерии готовности (acceptance)

1. Импорт компаний и контактов из xlsx/Google-таблицы с матчем контакт→компания; повторный импорт не плодит дубли.
2. Все компании после импорта видны в «Сигналах» как `new_signal`.
3. «В работу» авто-создаёт задачу `analyze_signal` и переводит компанию в `in_work`.
4. Завершение задачи всегда предлагает «следующий шаг» или «исключить»; активная компания не может остаться без открытой задачи незаметно — иначе она в «Фокусе».
5. Завершение задачи типа-метрики даёт `+1` в соответствующий счётчик; воронка считает уникальных.
6. Дашборд показывает KPI план/факт, метрики, воронку и «Фокус».
7. Плоскость гипотез: чекбоксы двигают прогресс-бар; независима от воронки.
8. Сервис собирается и деплоится по README одной последовательностью команд.

## 14. Первые шаги реализации (для Claude Code)
